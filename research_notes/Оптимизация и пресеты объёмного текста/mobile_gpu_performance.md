# Mobile GPU performance rules for WebGL1 effects (iPhone 11 / A13, Xiaomi with Adreno / Mali) — relevance to stacked-quad extruded text

Context for the reader: the current extruded-text approach draws 15–65 stacked alpha-blended quads per glyph, each fragment shader using `discard`. All notes below are judged against that approach. Research done 2026-10-22; ~25 tool calls; several official vendor pages (Arm developer docs, old Qualcomm QDN pages) now redirect or 404, which limited direct quotation.

## 1. Apple GPUs (A13): TBDR, Hidden Surface Removal, discard, blending, depth writes

### Takeaway
On Apple GPUs HSR only removes work hidden behind **opaque** fragments; anything that uses `discard` ("feedback" fragments) or blending ("translucent") cannot be culled ahead of shading and every covered layer is shaded. So 15–65 overlapping blended+discard layers means close to 15–65× shading of the glyph area every frame, and HSR gives no help. Apple's recommended order is opaque → discard → translucent.

### Cited Findings
- Apple GPUs (A11+) are TBDR: the GPU "defers ... the rendering phase for each tile until after it evaluates all the geometry for that tile", shades "only the visible primitives", and keeps results in on-chip tile memory, whose bandwidth is "many times faster" and energy cost "significantly less" than device memory — [Apple: Tailor your apps for Apple GPUs and TBDR](https://developer.apple.com/documentation/metal/tailor-your-apps-for-apple-gpus-and-tile-based-deferred-rendering)
- Same page: "A11 and later Apple GPUs also improve fragment discard performance" (no numbers given) — [Apple TBDR article](https://developer.apple.com/documentation/metal/tailor-your-apps-for-apple-gpus-and-tile-based-deferred-rendering)
- WWDC20 "Optimize Metal Performance for Apple silicon Macs" (10632; content applies to Apple GPUs in general): "Apple GPUs support hidden surface removal in hardware. The goal of HSR is to shade only visible pixels". Fragments fall into three classes: **opaque** ("any pixel beneath them can be rejected before shading"), **feedback** ("generated by fragment functions containing a discard statement or that return a depth value. Alpha tested foliage falls into this category"), **translucent** ("blend with their background like a smoke effect would") — [WWDC20 10632](https://developer.apple.com/videos/play/wwdc2020/10632)
- WWDC20 10632: "To maximize HSR efficiency draw each type of fragment together and then [in] the order shown. First opaque, then feedback, and finally translucent objects. Draw ordering within each category only matters for feedback and translucent fragments." — [WWDC20 10632](https://developer.apple.com/videos/play/wwdc2020/10632)
- WWDC20 10632: alpha blending and alpha testing make fragments non-opaque; write masks (not writing all color channels) also force shading of underlapping fragments ("some computation is wasted"); a depth pre-pass is unnecessary on Apple GPUs because HSR "can reject hidden fragments as well as depth pre-passes can, but without any additional costs" — [WWDC20 10632](https://developer.apple.com/videos/play/wwdc2020/10632)
- WWDC20 10602 ("Harness Apple GPUs with Metal"): HSR runs before fragment processing, tracks the frontmost opaque layer per pixel, is pixel-perfect and independent of submission order for opaque geometry — [WWDC20 10602](https://developer.apple.com/wwdc20/10602) (summarised via search snippet, transcript not fetched)
- WWDC20 10631 ("Bring your Metal app to Apple silicon Macs"): on TBDR the GPU does "blending and alpha testing without ever having to load from the full color buffer in memory" — i.e. blending itself is cheap in bandwidth (on-chip), the cost is the extra shading — [WWDC20 10631 index](https://nonstrict.eu/wwdcindex/wwdc2020/10631/) (search snippet)
- Imagination (PowerVR, the TBDR lineage Apple GPUs descend from): "Applications should avoid the use of the discard operation in the fragment shader as using it will not improve performance"; "alpha-tested primitives cannot write data to the depth buffer until the fragment shader has executed. These deferred depth writes can impact performance"; "an application should prefer alpha blending over discarding"; submit opaque → alpha-tested → blended — [Imagination: Do Not Use Discard](https://docs.imgtec.com/starter-guides/powervr-architecture/html/topics/rules/do-not-use-discard.html)
- Community view is split on whether blending is as harmful to HSR as discard on PowerVR-style hardware — [GameDev.net thread (opinion)](https://www.gamedev.net/forums/topic/656826-why-the-alphablend-is-a-better-choice-than-alphatest-to-implement-transparent-on-mobile-device/)

### Inferences
- For the stacked-quad text: `discard` makes every layer a "feedback" fragment AND blending makes it "translucent" — the worst of both classes. HSR can cull nothing between layers, so fragment cost ≈ (number of layers) × (pixel area of each layer's quad). `discard` does not save shading work (the shader already ran) and adds a dependency for depth; with depth writes off it mainly just suppresses the write.
- If layers are drawn opaque (no blending, no discard) with depth test+write, ordered so the front face is opaque, Apple HSR would shade each pixel ~once regardless of layer count — the single biggest win available on A13. Antialiased glyph edges then need another trick (e.g. one blended front layer only, or MSAA, which Apple implements efficiently per the TBDR article).
- Removing `discard` where the shader already outputs alpha=0 (blending makes those pixels invisible anyway) is cheap to try and per Imagination/Apple guidance can only help.
- Better still: collapse the extrusion into ONE full-coverage pass (single quad per glyph/line, shader computes the extrusion by sampling an SDF/atlas along the extrusion direction) so overdraw is 1×, trading fill for texture fetches/ALU in a loop (see section 2 caveats about loops).

### Gaps
- Apple publishes no per-operation cycle costs for discard or blending on A13; "improved discard performance" is unquantified.
- Not verified how WebKit's WebGL (ANGLE → Metal) maps `discard` and depth state; assumed to map directly to `discard_fragment` and Metal depth state.

## 2. Arm Mali and Qualcomm Adreno: early-Z / FPK / LRZ, discard, blending, overdraw, precision, branching

### Takeaway
Both vendors say the same thing: `discard` disables or degrades early depth rejection (Mali → late ZS; Adreno → no early-Z, LRZ falls back), blended layers are always fully processed, and the cure is fewer overlapping transparent layers. Qualcomm explicitly prefers alpha blending over discard, recommends half precision, and warns that non-uniform branches/loops cost GPRs and both-path execution.

### Cited Findings
- Arm (Mali): late Z-testing is needed when the shader can change values that affect visibility — modifying coverage, modifying depth, conditional `discard`; early and late ZS share one pipeline, creating dependencies between fragments — [Arm blog: Hidden surface removal methods in Mali GPUs](https://developer.arm.com/community/arm-community-blogs/b/mobile-graphics-and-gaming-blog/posts/hidden-surface-graphics-removal-methods-in-mali-gpus) (search summary; page later returned 404 on direct fetch)
- Arm (Peter Harris, Arm engineer, forum, ~2015, older source): "discard is just another form of transparency - we have to run the shader to determine if a fragment is discarded"; using discard for masking will "force everything to late-zs"; for GL_BLEND "we have to process every layer and load every texel to get the alpha values"; "the big issue with 2D games is often the sheer number of fragments which end up getting layered one of top of another"; advice: "Try and avoid both as much as possible" — [Arm Community forum "Translucent"](https://community.arm.com/support-forums/f/graphics-gaming-and-vr-forum/153/translucent/213)
- Arm: Forward Pixel Kill (FPK) still exists on newer Mali GPUs and performs some HSR even when the newer fragment pre-pass cannot be used — [Arm blog: Immortalis-G925 fragment prepass](https://developer.arm.com/community/arm-community-blogs/b/mobile-graphics-and-gaming-blog/posts/immortalis-g925-the-fragment-prepass) (search summary). FPK only kills fragments occluded by later *opaque* fragments (background: [Arm 2013 "Killing pixels" blog, old](https://developer.arm.com/community/arm-community-blogs/b/mobile-graphics-and-gaming-blog/posts/killing-pixels---a-new-optimization-for-shading-on-arm-mali-gpus))
- Qualcomm Adreno Game Developer Guide (current, docs.qualcomm.com):
  - "Avoid discarding pixels in the fragment shader": "If some pixels in a thread are killed and others are not, the shader still executes"; discard behaviour is hard to predict across drivers; if unavoidable, "the later in the frame a discard operation takes place, the better" — [Qualcomm: Adreno GPU on Mobile: Best Practices](https://docs.qualcomm.com/doc/80-78185-2/topic/mobile_best_practices.html)
  - Early Z is disabled when the fragment shader writes depth or uses discard; Adreno can reject occluded pixels "at up to 4x the drawn pixel fill rate" (only helps opaque, depth-tested content) — [same](https://docs.qualcomm.com/doc/80-78185-2/topic/mobile_best_practices.html)
  - Fixed-function blending can disable LRZ writes until the next clear; when combining passes "prefer using alpha blending to the alternatives" (discard, shader branching, stencil) — [same](https://docs.qualcomm.com/doc/80-78185-2/topic/mobile_best_practices.html)
  - Half precision: "Use strict half-precision types as much as possible"; medium precision makes the scalar ALU "much more efficient" — [same](https://docs.qualcomm.com/doc/80-78185-2/topic/mobile_best_practices.html)
  - Control flow: "Minimizing non-uniform looping and branching often helps reduce GPR and ALU usage"; branching on a compile-time constant is cheapest, branching on a value computed in the shader is worst — "the driver will probably execute both branches"; unrolled loops push texture fetches to the top and raise register pressure — [same](https://docs.qualcomm.com/doc/80-78185-2/topic/mobile_best_practices.html)
  - Framebuffer: "Invalidate framebuffer contents as early as possible"; use glClear to minimize GMEM loads/stores — [same](https://docs.qualcomm.com/doc/80-78185-2/topic/mobile_best_practices.html)
- Qualcomm FAQ (older QDN, now redirected): shaders using discard/clip "will go to full-resolution Z" — no LRZ benefit — [Qualcomm GDG FAQ (dead link, via search snippet)](https://developer.qualcomm.com/sites/default/files/docs/adreno-gpu/snapdragon-game-toolkit/gdg/gpu/faq.html); Igalia notes a shader that only discards can still use early LRZ but not early depth test — [Igalia: LRZ on Turnip (2021)](https://blogs.igalia.com/siglesias/2021/04/19/low-resolution-z-buffer-support-on-turnip/)
- MDN WebGL best practices: unconditional `highp` in fragment shaders "will prevent your content from working on some older mobile hardware"; use `#ifdef GL_FRAGMENT_PRECISION_HIGH` fallback; `mediump` "often results in corrupted rendering due to lack of precision (particularly mobile systems)"; `getShaderPrecisionFormat()` tells real support; "Do as much work as you can in the vertex shader"; batching draws helps; on tiled GPUs use `invalidateFramebuffer` (WebGL2) for unneeded attachments; `alpha:false` can have "a significant performance cost" on some platforms — [MDN: WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)
- Unity docs (secondary): on Adreno, lower precision can be faster via better register allocation/fast paths; rule of thumb is half precision for everything except positions and texture coordinates — [Unity manual: shader data types and precision](https://docs.unity.cn/2021.1/Documentation/Manual/SL-DataTypesAndPrecision.html)
- WebGL-on-mobile guide (secondary): tile-based mobile GPUs make overlapping transparent layers costly; reducing overdraw is a major lever — [abratabia WebGL mobile](https://abratabia.com/webgl/webgl-mobile.php)

### Inferences
- On Mali/Adreno (typical Xiaomi), the stacked-quad approach with discard is worst-case: late ZS on Mali, no early-Z/LRZ on Adreno, and blended layers all processed. Cost scales linearly with layer count × covered pixels.
- A ray-march/loop-in-shader single pass: keep the loop count a compile-time constant (`for (int i=0;i<N;i++)` with const N, as GLSL ES 1.00 requires anyway) and avoid data-dependent early `break` if warps would diverge; prefer `mediump` for color/accumulation math, `highp` only for UVs/positions; compare N texture fetches per pixel × 1 pass vs. 1 fetch per pixel × N layers — the fetch count is similar, but the single pass removes N−1 blend/ROP ops, N−1 shader launches, and per-fragment overhead.
- Pre-baking (render the extruded text once into a texture, then draw one quad per frame) removes almost all per-frame cost; only re-render when text/animation parameters change.

### Gaps
- Could not fetch the current Arm Mali GPU Best Practices guide text (developer.arm.com redirected to support.arm.com, which returned an empty page); its exact wording on discard/FPK/mediump is not quoted here.
- No vendor numbers on how much `mediump` saves on Mali-G52/G57 specifically.
- Did not find authoritative info on how WebKit/ANGLE-Metal translates GLSL `mediump` (to Metal `half` or `float`); behaviour on iPhone should be measured.

## 3. Fill-rate / fragment throughput figures and full-screen cost at DPR 2–3

### Takeaway
Hard GPixel/s figures for A13 / Adreno 6xx are not published by vendors; only Mali-G52 has an official per-core rate (2 pixels/clock/core). The practical approach is a budget formula: pixels touched per frame = Σ(layers × covered area × DPR²), compared against per-device measurement.

### Cited Findings
- Mali-G52: 2 pixels and 2 texels per clock per core, 1–4 cores — [AnandTech: Arm launches Mali-G52/G31](https://anandtech.com/show/12501); [GSMArena](https://www.gsmarena.com/arm_unveils_midrange_malig52_gpu_as_well_as_the_entrylevel_g31-news-29960.php). An Arm spec table lists the same (search summary of [Arm doc](https://documentation-service.arm.com/static/620e22c90ca305732a3a5dd0)).
- A13 GPU is a four-core design; AnandTech measured sustained GFXBench performance ~50–60% above iPhone XS (A12) — [Wccftech summary of AnandTech](https://wccftech.com/iphone-xs-vs-iphone-11-pro-graphics-performance-cpu-tests/amp/); [macerkopf](https://www.macerkopf.de/2019/10/17/anandtech-iphone11-pro-prozent-grafikleistung/)
- Adreno 618 (Snapdragon 730/730G) measured 14–30% faster than Adreno 616 in Notebookcheck tests; no fill-rate spec — [Notebookcheck comparison](https://www.notebookcheck.com/Adreno-610-vs-Mali-G52-MP2-vs-Adreno-618_9921_10399_9900.247532.0.html)
- MDN: consider reducing `canvas.width/height` while keeping CSS size constant to reduce cost — [MDN WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)

### Inferences
- Worked example (arithmetic only, no sourced clock): a text block 320×120 CSS px at DPR 3 = 960×360 ≈ 0.35 Mpx. With 65 layers each covering the block: ≈ 22 M fragments/frame → ≈ 1.35 G fragments/s at 60 fps. A Mali-G52 MC2 does 4 px/clock theoretical; even at ~1 GHz (assumed, unverified) that is ~4 Gpx/s peak *for trivial shaders*, so this text alone would eat roughly a third of peak fill on an entry Xiaomi — before shader ALU/texture cost and before the rest of the UI. At 15 layers it is ~5×less. Each layer's quad tightly fitting the glyph (not the whole block) reduces this a lot.
- iPhone 11 renders at DPR 2 (828×1792 panel), so pixel counts are ~0.44× of a DPR-3 device for the same CSS size; older Xiaomi are typically DPR 2.75–3 — rendering the text canvas at DPR ≤ 2 is a cheap, large saving (pixels scale with DPR²: 3² vs 2² = 2.25×).

### Gaps
- No authoritative GPixel/s for A13, Adreno 610/618/640, Mali-G57/G72 found (Notebookcheck/GFXBench pages did not expose fill-rate numbers). Recommend measuring on target devices instead.

## 4. Thermal throttling and rAF behaviour in mobile browsers / WebViews

### Takeaway
Heat comes from sustained load; any continuously running rAF loop that redraws (even a cheap one) keeps GPU/CPU clocks up. iOS caps rAF to 30 fps in Low Power Mode (intentional per WebKit) and throttles cross-origin iframes. The robust policy is render-on-demand: draw only when something changes, stop the loop when idle, and adapt resolution from frame timings since the web has no thermal API.

### Cited Findings
- WebKit: rAF throttled to 30 fps in Low Power Mode is intentional ("In fact the behavior in iOS 13 was a bug" — where it wasn't capped) — [WebKit bug 215745](https://bugs.webkit.org/show_bug.cgi?id=215745); original change proposed to save battery — [WebKit bug 168837](https://bugs.webkit.org/show_bug.cgi?id=168837)
- iOS throttles rAF to 30 fps in cross-origin iframes until the user interacts; Low Power Mode throttling applies also to CSS animations (2018–2020 sources) — [Popmotion](https://popmotion.io/blog/20180104-when-ios-throttles-requestanimationframe); [Motion.dev](https://motion.dev/magazine/when-browsers-throttle-requestanimationframe)
- Throttling is a sustained-load phenomenon: games can hold 60 fps for minutes then drop as the device heats; you won't see it in a measurement right after launch — [abratabia WebGL mobile](https://abratabia.com/webgl/webgl-mobile.php)
- Academic measurement (Pixel 2): throttling starts ~40 °C, big CPU cluster capped below half frequency by 47 °C, shutdown at 56 °C — [Southampton paper (tus)](https://eprints.soton.ac.uk/439709/1/tus_accepted_paper.pdf)
- Unity on-demand rendering: rendering static/menu screens at a lower frame rate "helps keep the device temperature from rising to the point where the CPU may be throttled" — [Unity OnDemandRendering](https://docs.unity.cn/ja/2019.4/ScriptReference/Rendering.OnDemandRendering.html)
- Qualcomm: MAILBOX present mode "can sometimes help with frame pacing/latency, but often can cost significant battery and generate significant heat for no benefit" (Vulkan-specific, but same principle: don't render frames nobody sees) — [Qualcomm best practices](https://docs.qualcomm.com/doc/80-78185-2/topic/mobile_best_practices.html)
- MDN: when not using rAF call `gl.flush()` for eager execution; with rAF it is not needed — [MDN WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)

### Inferences
- For the extruded text: animate only during entrance/count-up (finite duration), then either stop the loop (static frame stays on canvas since the buffer isn't cleared until next draw — compositing still works without preserveDrawingBuffer as long as you don't redraw) or swap to a cached bitmap. A constant idle shimmer at 60 fps is exactly the "sustained load" pattern that heats iPhones (matches project rule in CLAUDE.md).
- Telegram on iOS uses WKWebView; the Mini App is not a cross-origin iframe on mobile, so the iframe throttle likely doesn't apply there, but Low Power Mode 30 fps does — animations should be time-based, not frame-count-based.

### Gaps
- No source found quantifying heat from a "cheap" idle rAF loop vs. stopped loop in WKWebView; nor whether WKWebView in Telegram follows Safari's Low Power Mode cap exactly (very likely, same WebKit, but unverified).
- No browser thermal API exists; inferring from frame-time drift is the only option (per abratabia).

## 5. Canvas/WebGL specifics on iOS WKWebView; OffscreenCanvas & Workers; readback

### Takeaway
WebKit keeps at most ~16 active WebGL contexts (oldest is lost), caps total canvas backing memory (384 MB reported on iOS 15, varies by device/version) and single-canvas area at 16.7 Mpx. OffscreenCanvas 2D works in workers from Safari/iOS 16.4; WebGL in OffscreenCanvas from Safari 17 / iOS 17. FontFace support in workers was implemented in WebKit (bug 224178), so drawing text with a custom font in a worker is plausible on iOS 16.4+, but needs device testing. `getImageData` on GPU canvases forces synchronous readback; `willReadFrequently:true` switches to a CPU canvas.

### Cited Findings
- WebKit adopted the 16-concurrent-active-WebGL-contexts limit; creating more loses the oldest with a console warning — [WebKit commit "Creating a large number of WebGL contexts should recycle older contexts" (2016)](https://webkit.googlesource.com/WebKit/+/70e10861eb2fbd9d0862fd8702874c25ae5d8bfd%5E%21); [layout test](https://webkit.googlesource.com/WebKit/+/master/LayoutTests/webgl/max-active-contexts-oldest-context-lost-expected.txt). A 2019 bug saw the limit drop to 8 after video textures (fixed) — [WebKit bug 200031](https://bugs.webkit.org/show_bug.cgi?id=200031)
- iOS Safari "Total canvas memory use exceeds the maximum limit (384 MB)" (iOS 15; lower earlier, device-specific; other reports 224/448/576 MB); Safari holds released canvases for a while — shrink to 1×1 to free — [WebKit bug 195325](https://bugs.webkit.org/show_bug.cgi?id=195325); [PQINA](https://www.pqina.nl/blog/total-canvas-memory-use-exceeds-the-maximum-limit/); [Apple forums](https://developer.apple.com/forums/thread/687866). Separate limit: canvas area > 16,777,216 px rejected — [PQINA](https://pqina.nl/blog/canvas-area-exceeds-the-maximum-limit/)
- Safari 16.4 shipped OffscreenCanvas with 2D context only (`getContext("webgl")` in worker returned null, breaking naive feature detection) — [WebKit bug 253431](https://bugs.webkit.org/show_bug.cgi?id=253431). Safari 17 shipped WebGL in OffscreenCanvas; requires iOS 17 / iPadOS 17 / macOS Sonoma (per WebKit's Jen Simmons in bug thread) — [WebKit bug 183720](https://bugs.webkit.org/show_bug.cgi?id=183720)
- WebKit implemented FontFace in workers for OffscreenCanvas (bug 224178, resolved fixed); worker `setFont` uses a worker-safe parser; earlier (2020) font functions worked only on main thread — [WebKit bug 224178](https://www2.webkit.org/show_bug.cgi?id=224178); [WebKit r270102](https://trac.webkit.org/r270102); [WebKit source](https://webkit.googlesource.com/WebKit/+/master/Source/WebCore/html/canvas/OffscreenCanvasRenderingContext2D.cpp)
- `getImageData` on a GPU-backed canvas "triggers a synchronous read-back operation, which severely degrades performance" — [WebKit bug 65622 (2011, old)](https://bugs.webkit.org/show_bug.cgi?id=65622); browsers are moving away from CPU/GPU heuristics, so repeated readers must pass `{willReadFrequently:true}` — [WebKit bug 235196 (2022)](https://bugs.webkit.org/show_bug.cgi?id=235196); Chrome 106+ logs a console warning without it — [Dynamsoft note](https://dynamsoft.com/web-twain/docs/faq/chrome-106-107-warning.html)
- MDN: `willReadFrequently` "will force the use of a software (instead of hardware accelerated) 2D canvas and can save memory when calling getImageData() frequently"; `powerPreference` values `default` / `high-performance` / `low-power`; `desynchronized` "hints the user agent to reduce the latency by desynchronizing the canvas paint cycle from the event loop"; `preserveDrawingBuffer:true` keeps buffers uncleared — [MDN getContext](https://developer.mozilla.org/en-US/docs/Web/API/HTMLCanvasElement/getContext)
- MDN: iOS needs `highp sampler2D` for float textures or samples are lowp; iOS supports 16-bit float render targets but not 32-bit (WebKit 2020) — [MDN best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices); [WebKit bug 216010](https://bugs.webkit.org/show_bug.cgi?id=216010)

### Inferences
- Each extra WebGL canvas (Горн, glow, extruded text) counts toward the ~16 limit and the canvas memory cap; prefer one shared context or bake text into a 2D canvas/texture.
- `preserveDrawingBuffer:true` on tiled GPUs forces a tile store/copy of the previous frame — keep it false (default). `antialias:true` allocates MSAA (cheap on Apple per TBDR article, more costly on Mali/Adreno bandwidth); for SDF/atlas text, shader-side AA with `antialias:false` is usually enough. `premultipliedAlpha:true` (default) matches the compositor; non-premultiplied requires an extra conversion (spec-level reasoning, not sourced here).
- Atlas generation of glyphs (currently being moved to a background worker per recent commits) is feasible on iOS 16.4+ with OffscreenCanvas 2D; WebGL-in-worker needs iOS 17+, so keep main-thread fallback. Feature-detect by actually calling `getContext` in the worker, not by `typeof OffscreenCanvas`.
- If the atlas is built on a 2D canvas and read via `getImageData` (e.g. for SDF computation), create that context with `willReadFrequently:true`; if it's uploaded straight to WebGL via `texImage2D(canvas)`, readback isn't needed.

### Gaps
- `desynchronized` and `powerPreference` support/effect in WKWebView not confirmed (MDN compat table not retrievable). iPhones have a single GPU, so `powerPreference` likely only matters on multi-GPU Macs (inference).
- Not confirmed in Safari release notes which iOS version ships FontFace-in-workers; needs on-device test (`self.fonts.add(face); await face.load(); ctx.font=...; ctx.fillText`).
- WKWebView-specific per-process memory limits (jetsam) not found.

## 6. Measuring: profiling WebGL on iPhone and Android

### Takeaway
On iPhone: Safari Web Inspector (Mac, Develop menu → device) Timeline shows JS/rendering and `drawElements` time, and memory; it is known to be unstable on heavy WebGL pages. Native GPU counters for WebKit content need Xcode/Instruments (Metal System Trace) — not confirmed to attach to WKWebView. On Android: Chrome remote DevTools Performance panel, plus vendor tools (Snapdragon Profiler, Arm Streamline) for GPU counters. In-app FPS/frame-time overlay remains the most reliable cross-device signal.

### Cited Findings
- Safari Web Inspector Timeline was used to find most frame time in `drawElements` on a WebGL page — [WebKit bug 223100](https://bugs.webkit.org/show_bug.cgi?id=223100); recording from an iPhone via Mac Develop menu → Timeline; reports of devtools crashing on large WebGL apps — [Apple Developer Forums 730731](https://developer.apple.com/forums/thread/730731)
- Web Inspector Timeline memory section used for WebGL memory on iOS — [Unity issue tracker](https://issuetracker.unity.com/issues/11224/memory-usage-increased-in-newer-versions-when-using-safari)
- Metal System Trace in Instruments profiles CPU/GPU for Metal apps — [WWDC15 610](https://nonstrict.eu/wwdcindex/wwdc2015/610/); WWDC20 10632 recommends Metal System Trace and Xcode Pipeline Statistics; GPU counters covered in WWDC20 10603 — [WWDC20 10632](https://developer.apple.com/videos/play/wwdc2020/10632)
- Qualcomm recommends the Adreno Offline Compiler for shader instruction/GPR analysis — [Qualcomm best practices](https://docs.qualcomm.com/doc/80-78185-2/topic/mobile_best_practices.html) (search summary)
- Adaptive resolution from rAF timestamps (lower render resolution when frames miss 16.7 ms) — [abratabia WebGL mobile](https://abratabia.com/webgl/webgl-mobile.php)

### Inferences
- Practical test protocol: fixed scenario (e.g. 60 s of text animation + 5 min idle), record frame times with the existing Дебаг → «Замер» overlay, compare layer counts (15/30/65) and DPR (2 vs 3); for heat, run 10+ minutes and watch frame-time drift (throttling only shows after minutes).
- A quick fill-rate-bound check: shrink the canvas resolution by half; if frame time drops ~4×, the effect is fragment/fill bound (which stacked layers are expected to be).

### Gaps
- Did not verify that Instruments' Metal System Trace / Xcode GPU capture can attach to WebKit's GPU process for Safari or a third-party WKWebView (Telegram); likely restricted.
- No current official docs fetched for Chrome tracing/Perfetto GPU tracks, Snapdragon Profiler, or Arm Performance Studio/Streamline with Android WebView.
