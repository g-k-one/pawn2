# Optimizing a WebGL1 sphere-traced extruded-SDF text renderer for mobile (iPhone 11, Adreno 6xx / Mali-G52)

Context of our renderer (for the report writer): box proxy per glyph (12 triangles), fragment shader marches up to 56 steps through an 8-bit LUMINANCE SDF atlas plus an RGBA mask with edge normals, coverage AA from the closest-miss distance, back-to-front sort, premultiplied blending, no discard, per-letter transforms from uniform arrays (3 x vec4 x 32 letters in the VS), render only while animating, one WebGL canvas per label, DPR capped at 2.

Research budget note: Keinert et al. and Bán & Valasek full texts were not retrievable (cert error / HTTP 403), so their numeric speedups are NOT in these notes. Algorithm descriptions marked "(from prior knowledge, not re-verified)" are inferences, not cited facts.

## 1. Adaptive quality: dynamic resolution, step-count reduction, shader variants

### Takeaway
The standard web approach is to shrink `canvas.width/height` while keeping the CSS size fixed, but community experience says continuous FPS-driven switching causes visible instability and feedback loops; use a few discrete levels with hysteresis (or pick once at startup). For our "render only while animating" model, the cleanest variant is: lower internal resolution / fewer steps during fast motion, and one full-quality frame when the animation settles. Precompile all variants up front (ideally with `KHR_parallel_shader_compile`) so switching is only a `useProgram`.

### Cited Findings
- MDN recommends rendering to a smaller back buffer: "Consider reducing canvas.width and height and keeping canvas.style.width and height at a constant size." — [MDN WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)
- MDN warns `canvas.width = width * devicePixelRatio` "will cause moire artifacts with non-integer values of devicePixelRatio"; suggests `ResizeObserver` with `device-pixel-content-box` for the true device-pixel size and pre-snapping the canvas to whole device pixels. — [MDN WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)
- MDN: compile all shaders first, then link all programs, check status afterwards; "Don't check shader compile status unless linking fails" (it is synchronous and breaks pipelining); prefer `KHR_parallel_shader_compile`, which provides a non-blocking `COMPLETION_STATUS_KHR` query. — [MDN WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)
- MDN: `getError`/`getParameter` cause synchronous stalls; "Even basic requests can take as long as 1ms". — [MDN WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)
- MDN: "Most texture uploads from DOM elements will incur a processing pass that will temporarily switch GL Programs internally, causing a pipeline flush" — do uploads before drawing. (Relevant to atlas rebuilds when text changes.) — [MDN WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)
- MDN gives no numeric cost for program switching. — [MDN WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)
- three.js forum: constantly shifting pixel ratio based on FPS makes the image feel unstable; a feedback loop appears (low FPS -> lower ratio -> higher FPS -> ratio restored -> repeat); one poster recommends measuring once at startup and fixing resolution; another suggests stepping the ratio down until a target such as 55 FPS is reached. — [three.js forum: Changing pixelRatio based on fps](https://discourse.threejs.org/t/changing-pixelratio-based-on-fps-good-or-bad-idea/34563), [page 2](https://discourse.threejs.org/t/changing-pixelratio-based-on-fps-good-or-bad-idea/34563?page=2)
- A three.js adaptive-DPR tutorial samples FPS over a short window, lowers DPR when below a target and raises it above; sample code uses a 45 FPS target and a 0.9 multiplier, clamped to a range (per search snippet). — [sbcode adaptive dpr](https://sbcode.net/tsl/adaptive-dpr)
- React-three drei ships `AdaptiveDpr` (performance-driven DPR between lower/upper bounds). — [drei performance docs](https://tessl.io/registry/tessl/npm-react-three--drei/files/docs/performance.md)
- three.js forum: `setPixelRatio(window.devicePixelRatio)` + `setSize` can create a render buffer much larger than the physical screen with fractional scaling; page zoom can change the ratio without three.js adjusting. — [three.js forum: HiDPI + fractional scaling](https://discourse.threejs.org/t/hidpi-fractional-scaling-performance-pitfalls-and-best-practices/87114)
- Unity's dynamic resolution scales render targets "to reduce workload on the GPU"; scaling is gradual when frame rate drops "and can be almost unnoticeable"; driven by `ScalableBufferManager` (width/height scale factors) + `FrameTimingManager` (detects CPU/GPU slowdown). Supported on iOS only with Metal, Android only with Vulkan. — [Unity Manual: Dynamic Resolution](https://docs.unity3d.com/2022.3/Documentation/Manual/DynamicResolution.html)

### Inferences
- Resizing the canvas (setting `canvas.width/height`) reallocates and clears the drawing buffer (HTML canvas spec behaviour, not re-fetched here), so do it only at discrete moments: e.g. 3 levels (1.0 / 0.75 / 0.5 x the capped DPR), switch down at most once per animation and back up only on the final "settled" frame. With render-only-while-animating, the settled frame is a single full-quality render, so its cost is a one-off and never sustained.
- Motion hides resolution loss: during a fast pop/slam/drop the canvas can run at 0.5–0.75 scale; the eye sees the sharp version when it stops. This is cheaper than reducing steps, because resolution scales cost quadratically (0.75 scale = 56% of pixels, 0.5 = 25%), while step count scales roughly linearly and only for pixels that actually need many steps.
- Step-count variants: compile `#define MAX_STEPS 16 / 24 / 40` (plus maybe the current 56) at startup (batched compile + link, `KHR_parallel_shader_compile` if present). A `useProgram` + re-setting uniforms per frame is negligible next to a 56-step raymarch. Uniform values are per-program, so all uniforms must be re-uploaded after switching (or keep the uniform-setting path generic).
- Frame-time signal: use rAF timestamps averaged over 0.5–1 s with hysteresis (e.g. drop a level if avg > 20 ms for 30 frames, raise only on a new animation). Avoid `getParameter`/`getError` in the loop (up to 1 ms each per MDN). Remember iOS Low Power Mode caps rAF at 30 fps (see section 6) — a 33 ms frame there is the cap, not GPU overload; detect a stable ~33.3 ms period and do not downgrade because of it.
- Alternative to resizing the canvas: keep the canvas size fixed and draw into a low-res FBO, then upscale with one textured quad. This avoids buffer reallocation but costs an extra pass and FBO memory; with our small labels, plain canvas resize at animation start is probably simpler.

### Gaps
- No measured numbers for the cost of `canvas.width` changes or `useProgram` switching on iOS WKWebView / Android WebView were found.
- No source with mobile-browser measurements of dynamic resolution specifically for raymarchers.

## 2. Precision: mediump vs highp on Apple, Adreno, Mali; what needs highp

### Takeaway
On mobile, mediump really is lower precision (FP16-class, 10-bit mantissa) and can run up to ~2x faster in ALU on GPUs with FP16 paths, but it breaks ray-march accumulators and atlas UVs. Use the `GL_FRAGMENT_PRECISION_HIGH` pattern, keep ray position/t, atlas UVs and transforms highp, and consider mediump only for color/shading math. Safari's ANGLE-Metal path compiles shaders with fast-math, which is a separate robustness risk for NaN/large intermediates.

### Cited Findings
- Recommended fallback pattern (MDN): `#ifdef GL_FRAGMENT_PRECISION_HIGH precision highp float; #else precision mediump float; #endif`; "Using highp precision unconditionally in fragment shaders will prevent your content from working on some older mobile hardware." — [MDN WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)
- ESSL 1.00 minimum guarantees (MDN): highp float range (-2^62, 2^62), relative precision 2^-16; mediump range (-2^14, 2^14), relative precision 2^-10, min above zero 2^-14; lowp (-2, 2), 2^-8 absolute. highp ints only int17, mediump int11. — [MDN WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)
- MDN: on iOS, a float texture needs `highp sampler2D`, "or it will very painfully give you lowp texture samples! (+/-2.0 max ...)". — [MDN WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)
- `getShaderPrecisionFormat()` reports what the device actually supports. — [MDN WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)
- On desktop mediump/lowp typically run as highp; on mobile they can actually run at lower precision, so precision bugs may show only on phones. — [WebGL Fundamentals: cross-platform issues](https://webglfundamentals.org/webgl/lessons/webgl-cross-platform-issues.html)
- PowerVR (Imagination) guidance: mediump = 16-bit float, which "theoretically" doubles FP throughput over FP32/highp. — [Imagination: Do Prefer Lower Data Precision](https://docs.imgtec.com/starter-guides/powervr-architecture/html/topics/rules/do-prefer-lower-data-precision.html)
- Unity: on iOS/tvOS `half` maps to `min16float` ("lower precision than float, so you might quickly reach the precision limit and experience visual issues"). — [Unity: Metal requirements](https://docs.unity.cn/2023.3/Documentation/Manual/metal-requirements-and-compatibility.html)
- Adreno: an Adreno 320 developer reported mediump implemented as fixed point (old GPU); Flutter's Impeller switched a Gaussian downsample shader from mediump to highp to fix sampling problems on Adreno. — [Qualcomm developer forum](https://developer.qualcomm.com/comment/8162); [Flutter engine commit #57212](https://dart.googlesource.com/external/github.com/flutter/engine/+/ad0272918c56ffcd9b195753a3c4138aa3cb5e32%5E%21/)
- Adreno OpenCL user found no speedup from fp16 on Adreno 430 despite half ALU use — the 2x gain does not always materialize (anecdotal). — [Qualcomm developer forum](https://developer.qualcomm.com/comment/9098)
- Arm's Mali Offline Compiler gives per-shader cycle cost (including FP16 vs FP32 effects) for Bifrost GPUs such as Mali-G52 — the practical way to measure on Mali. — [Arm: Mali Offline Compiler 7](https://developer.arm.com/community/arm-community-blogs/b/mobile-graphics-and-gaming-blog/posts/accelerating-shader-programs-with-mali-offline-compiler-7)
- WebKit bug 237434 (open since March 2022, Safari 15 / iOS 15, Apple Silicon): precision jitter caused by "ffast-math" compilation of Metal shaders generated from WebGL GLSL; "Chrome ANGLE/Metal does not do ffast-math but Safari does"; workaround: keep intermediate values within the 32-bit float domain; Kenneth Russell: "there's no global way to force-disable the use of fast math". — [WebKit Bug 237434](https://bugs.webkit.org/show_bug.cgi?id=237434)
- ANGLE has a feature flag (disabled by default) that forces highp to mediump in fragment shaders. — [ANGLE change (Android mirror)](https://android.googlesource.com/platform/external/angle/+/e249239c54)

### Inferences
- Concrete error budget from the ESSL numbers: mediump has ~11 significant bits. An atlas UV in [0.5, 1.0) is quantized to 2^-11 = 1/2048. For a 1024 px atlas that is half a texel — bilinear SDF reconstruction becomes steppy/wobbly. For a 2048 px atlas it is one full texel. => atlas UVs and any value that feeds `texture2D` coordinates must be highp.
- Ray parameter `t` and ray position: with relative error 2^-10, at t = 10 units the step error is ~0.01 units; accumulated over 30–56 steps this causes surface "swimming" or missed thin strokes. Keep `ro`, `rd`, `t`, `p` highp.
- Fine for mediump (likely safe, inference): final color, lighting dot products, fresnel/spec terms, coverage alpha. Mixed-precision gains in WebGL1 are hard to control (one default precision per shader; per-variable qualifiers are allowed), so the realistic win is small; measure before doing it.
- Uniform precision mismatch rule (GLSL ES 1.00 spec, from prior knowledge, not re-fetched): a uniform declared in both VS and FS must have the same precision, otherwise link fails. The VS default float precision is highp, the FS has none — so a uniform shared by both (e.g. `uTime`, `uRes`) must be declared with explicit `highp` in the FS (or the FS default must be highp). On a device without `GL_FRAGMENT_PRECISION_HIGH`, such shared uniforms cannot be highp in the FS -> simply don't share uniforms between stages (duplicate under different names), or pass via varyings.
- Safari fast-math: do not rely on `isnan`/`isinf`, division by zero producing inf, or huge sentinel values (e.g. `t = 1e30`) — fast-math may reorder or drop them. Use modest sentinels (e.g. 1e4) and explicit clamps; guard `1.0/rd` for the ray-box slab test with `sign(rd)*max(abs(rd),1e-6)`.
- iPhone 11 (A13): Apple GPUs have native FP16 ALUs (well known; not sourced here), so if WebKit's ANGLE Metal emits `half` for mediump the shading part could benefit — but see Gaps.

### Gaps
- Could not confirm whether WebKit's ANGLE-Metal translator emits Metal `half` for GLSL mediump or simply emits `float` everywhere. Need: ANGLE `TranslatorMetalDirect` source, or empirical test with `getShaderPrecisionFormat(FRAGMENT_SHADER, MEDIUM_FLOAT)` + a precision-probe shader on iPhone 11.
- No vendor-published FP16:FP32 throughput ratio for Adreno 6xx or Mali-G52 was found in this session.

## 3. WebGL1 limits that matter and alternatives to big uniform arrays

### Takeaway
Our current 96 vec4 (3 x 32) in the VS fits the WebGL1 guaranteed 128 and the practical floor of 256 on every reported device (iOS reports >= 1024), so it is safe today; but `ANGLE_instanced_arrays` (iOS 100%, Android 99.93%) is the better structure: one unit-box mesh, 3 per-instance vec4 attributes, one draw call, no letter cap and no dynamic uniform indexing. Vertex texture fetch is also universally available in current survey data, but instanced attributes are simpler.

### Cited Findings
- Spec minimums WebGL1: 128 vertex / 16 fragment uniform vectors, 8 attributes, 8 varyings, 8 texture units total, vertex texture units minimum 0; ~97% of devices support at least 4 vertex texture units (older figure). — [WebGL Fundamentals: cross-platform issues](https://webglfundamentals.org/webgl/lessons/webgl-cross-platform-issues.html)
- MDN "effectively all systems support at least": MAX_VERTEX_UNIFORM_VECTORS 128, MAX_FRAGMENT_UNIFORM_VECTORS 64, MAX_VARYING_VECTORS 8, MAX_VERTEX_ATTRIBS 16, MAX_VERTEX_TEXTURE_IMAGE_UNITS 4, MAX_TEXTURE_IMAGE_UNITS 8, MAX_TEXTURE_SIZE 4096. — [MDN WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)
- web3dsurvey MAX_VERTEX_UNIFORM_VECTORS: overall >= 256 100%, >= 512 96%, >= 2047 58%; Android >= 256 100%, >= 512 59%, 4095 11%; iOS >= 1024 100%; Safari >= 1024 100%; Samsung Internet >= 256 100%, >= 1024 52%. — [web3dsurvey MAX_VERTEX_UNIFORM_VECTORS](https://web3dsurvey.com/webgl/parameters/MAX_VERTEX_UNIFORM_VECTORS)
- web3dsurvey MAX_FRAGMENT_UNIFORM_VECTORS (as returned by the page fetch): overall >= 256 100%, >= 512 96%; Android >= 256 100%, >= 1024 59%; iOS >= 1024 100%. NOTE: the search snippet for the same page mentioned values 64/112/128/220/224 also present — possible inconsistency between snippet and current page; MDN's universal floor is 64. — [web3dsurvey MAX_FRAGMENT_UNIFORM_VECTORS](https://web3dsurvey.com/webgl/parameters/MAX_FRAGMENT_UNIFORM_VECTORS); [MDN](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)
- Historical: iOS Safari (2014) reported a hardcoded 64 fragment uniform vectors even on hardware supporting 224 (bug closed invalid). — [WebKit Bug 133636](https://bugs.webkit.org/show_bug.cgi?id=133636)
- web3dsurvey MAX_VERTEX_TEXTURE_IMAGE_UNITS: overall >= 16 100% (>= 24 14%, >= 32 13%); Android >= 16 100%; iOS >= 16 100%. — [web3dsurvey MAX_VERTEX_TEXTURE_IMAGE_UNITS](https://web3dsurvey.com/webgl/parameters/MAX_VERTEX_TEXTURE_IMAGE_UNITS) (contrast: older/conservative figures of 4 from MDN and "~97% >= 4" from WebGL Fundamentals)
- web3dsurvey MAX_VARYING_VECTORS: overall 15 = 1%, 30 = 68%, 31 = 20%; Android: 15 = 9%, 31 = 82%; iOS >= 31 100%. — [web3dsurvey MAX_VARYING_VECTORS](https://web3dsurvey.com/webgl/parameters/MAX_VARYING_VECTORS)
- `ANGLE_instanced_arrays`: 99.7% overall, iOS 100%, Android 99.93%; Safari iOS supported since iOS 8. — [web3dsurvey ANGLE_instanced_arrays](https://web3dsurvey.com/webgl/extensions/ANGLE_instanced_arrays); [caniuse](https://caniuse.com/wf-angle-instanced-arrays)
- `ANGLE_instanced_arrays`, `OES_vertex_array_object`, `OES_element_index_uint` are "almost universal" in WebGL1; `OES_texture_float_linear` is often missing on mobile. — [WebGL Fundamentals: cross-platform issues](https://webglfundamentals.org/webgl/lessons/webgl-cross-platform-issues.html)
- Uniform packing is not guaranteed to be perfect across drivers — stay well under the limit. — [WebGL Fundamentals: cross-platform issues](https://webglfundamentals.org/webgl/lessons/webgl-cross-platform-issues.html)

### Inferences
- Budget check today: 96 vec4 for letters + camera/matrices (~8–12 vec4) ≈ 108 — under the 128 spec floor and far below the 256 practical floor. Raising to 64 letters (192 vec4) is still safe on every surveyed device (Android min 256) but no longer within the spec guarantee.
- Instancing plan: a single unit box (8 vertices + 36 indices, or 14-vertex strip) as the base mesh; per-instance attributes `aA, aB, aC` (3 x vec4) with `vertexAttribDivisorANGLE(loc, 1)`; total attributes = 1 + 3 = 4 (spec floor 8). Benefits: one `drawElementsInstancedANGLE` per label, no 32-letter cap, no dynamic indexing of uniform arrays (which on some mobile compilers is slower than attribute fetch), and per-frame updates become one `bufferSubData` of N x 48 bytes. Back-to-front order = write instances in sorted order into the buffer.
- Varyings: keep the VS->FS interface small (ray origin/dir in glyph-local space + glyph id/atlas rect ≈ 3–4 vec4); all devices give >= 8 (practically >= 15).
- Vertex texture fetch: survey says >= 16 VS texture units on all reporting devices, but float textures need `OES_texture_float` and on iOS a `highp sampler2D`; RGBA8 textures would need manual decoding. Instanced attributes avoid all that.
- Each glyph needs only one texture fetch path in FS: 2 samplers (SDF + mask) are fine against the 8-unit floor.

### Gaps
- No direct survey data split by GPU family (Adreno 6xx vs Mali-G52) for these parameters; survey splits only by OS/browser.

## 4. Multiple labels: many contexts vs one shared canvas

### Takeaway
Browsers (including Safari) cap active WebGL contexts at about 16 and silently kill the oldest; in some iOS conditions the effective limit is 8, and iOS also loses contexts on backgrounding. One canvas per label therefore does not scale and duplicates shader compiles and atlases. The robust pattern is one shared context: either one overlay canvas with `viewport`+`scissor` per label, or (where labels must live inside DOM flow) a shared context rendering and copying out — but the copy path is engine-dependent and slow outside Chromium.

### Cited Findings
- WebKit (2016) follows other browsers' limit of 16 concurrent active WebGL contexts; creating more loses the oldest (console: "Too many active WebGL contexts. Oldest context will be lost."), and the lost context may not be recoverable via `preventDefault()` in `webglcontextlost`. — [WebKit commit: recycle older contexts](https://webkit.googlesource.com/WebKit/+/70e10861eb2fbd9d0862fd8702874c25ae5d8bfd)
- WebKit bug (2019): with video textures, max active contexts suddenly 8; further creation returned null and then crashed the tab. — [WebKit Bug 200031](https://bugs.webkit.org/show_bug.cgi?id=200031)
- Reports of "WebGL: context lost" after backgrounding on iOS 16.7, 17 and 18; sometimes a context cannot be re-created until the browser is killed. — [PlayCanvas forum: iOS 17 context lost](https://forum.playcanvas.com/t/ios-17-x-webgl-context-lost/33420); [WebKit Bug 261331](https://bugs.webkit.org/show_bug.cgi?id=261331); [WebKit Bug 262628](https://bugs.webkit.org/show_bug.cgi?id=262628)
- WHATWG: sites wanting many live 3D views on a page find "creating multiple WebGL contexts per page is too inefficient". — [WHATWG WorkerCanvas](https://wiki.whatwg.org/wiki/WorkerCanvas2)
- Single canvas, multiple regions: set `gl.viewport` and `gl.scissor` to each region and enable the scissor test (`gl.clear` ignores viewport, so scissor is needed); suits non-overlapping views; three.js community recommends one fixed full-screen canvas + scissor rendering into each div's rect; drei `<View>` does this ("multiple views with a single, performant canvas"). — [WebGL Fundamentals: multiple views](https://webglfundamentals.org/webgl/lessons/webgl-multiple-views.html); [three.js forum](https://discourse.threejs.org/t/multiple-views-controls-in-them-responsive-media-queries/47085); [drei View](https://drei.docs.pmnd.rs/portals/view)
- One context feeding many canvases via `transferToImageBitmap` -> `transferFromImageBitmap`: Firefox "unusably slow" (~15 FPS on an RTX 4070); Chromium avoids the CPU readback with GPU compositing (wraps a GPU shared image). — [Mozilla Bug 1864882](https://bugzilla.mozilla.org/show_bug.cgi?id=1864882)
- WebKit discussion: ImageBitmap "is not implemented to be an optimisation across multiple Context2D and WebGL elements" in WebKit. — [WebKit Bug 234920](https://bugs.webkit.org/show_bug.cgi?id=234920)
- Resizing a shared offscreen render target per view is expensive; mixed view sizes become a bottleneck. — [W3C public-webapps-github, Greggman 2018](https://lists.w3.org/Archives/Public/public-webapps-github/2018Apr/1543.html)

### Inferences
- Recommended for Pawn: one context per screen (or one global), with a `position:fixed; pointer-events:none` overlay canvas; each label registers its DOM rect; per frame, only animating labels are drawn with scissor+viewport into their rect. One atlas texture and one set of compiled programs serve all labels; Forge (our particle engine, also WebGL) could even share the same context to stay well under the 16 limit. Caveat: overlay z-order versus DOM elements (sheets/modals over the label) must be handled by hiding the label region or the canvas.
- Cost of the overlay approach: a full-screen canvas at DPR 2 is a large back buffer (iPhone 11: 828x1792 px at DPR 2 = ~1.5 M px, ~6 MB RGBA) even if only small regions are drawn; compositing an idle transparent full-screen canvas still costs. Mitigation: size the overlay to the union rect of active labels, or `display:none` it when idle (consistent with our existing "Forge canvas hidden when idle" rule).
- The 2D-canvas copy path (`drawImage(webglCanvas)` into per-label 2D canvases) likely forces a GPU readback or extra copy on WebKit; avoid on iOS unless measured.
- Context-loss handling is mandatory regardless: listen for `webglcontextlost` (`preventDefault`) / `webglcontextrestored`, rebuild programs and atlas, and fall back to flat text if restore fails.

### Gaps
- No current (2024–2026) official number for iOS 17/18 WKWebView context limit; 16 is from 2016 WebKit code, 8 from a 2019 edge case.
- No benchmark found comparing N canvases vs one scissored canvas on mobile.

## 5. Sphere-tracing tricks for an extruded 2D SDF

### Takeaway
The published accelerators are over-relaxation (Keinert 2014, safe fallback) and its automatic variant (Bán & Valasek 2023), bounding-volume clipping and a screen-space metric for picking a hit when the march does not converge. For an extruded 2D SDF, the bigger structural wins are analytic: clip the ray to the glyph box, test the front cap with one fetch, march in 2D with steps scaled by 1/|rd.xy|, and refine the hit with one secant step — this likely makes most pixels cost 1–6 fetches instead of up to 56.

### Cited Findings
- Keinert et al., "Enhanced Sphere Tracing" (STAG 2014; extended as "Improved Ray Casting of Procedural Distance Bounds", JGT 17(4) 2015): a safe over-relaxation method that accelerates sphere tracing without missing intersections; dynamic prevention of self-intersections; faster intersection test for convex objects inside convex bounding volumes; a screen-space metric to choose a good intersection candidate when tracing does not converge; a fixed-point iteration to reduce discontinuity artifacts. — [FAU LGDV: Enhanced Sphere Tracing](https://www.lgdv.tf.fau.de/publicationen/enhanced-sphere-tracing); [Eurographics DL](https://diglib.eg.org/handle/10.2312/stag.20141233.001-008); [FAU CRIS (JGT 2015)](https://cris.fau.de/publications/200539563/)
- Bán & Valasek, "Automatic Step Size Relaxation in Sphere Tracing" (Eurographics 2023 short paper): scales step sizes automatically from previous iterations; takes significantly fewer robustness-preserving fallback steps because it generates fewer invalid over-relaxed steps; Figure 1 compares enhanced sphere tracing (ω = 0.88 per the snippet's parameterization), relaxed sphere tracing (ω = 1.5) and the auto-relaxed method by average step count. — [Eurographics DL entry](https://unpaywall.org/10.2312%2FEGS.20231014)
- Typical loop: stop when distance < threshold and cap iterations (Cambridge course example: 0.001 threshold, 50 steps; visualize step count as brightness). — [Cambridge Further Graphics: Ray Marching and SDFs](https://www.cl.cam.ac.uk/teaching/1718/FGraphics/1.%20Ray%20Marching%20and%20Signed%20Distance%20Fields.pdf)
- Reducing the step budget makes grazing rays fail first; raising epsilon makes the surface appear to inflate. — [GameDev.net shaderlab: raymarching a sphere](https://gamedev.net/shaderlab/12-raymarching-a-sphere/)
- Epsilon can be treated as a cone radius that grows with distance (pixel footprint ≈ pixel world width x t, half of the smaller dimension); described by its author as a rough heuristic. — [pouet.net thread](https://www.pouet.net/topic.php?which=8785)
- `OES_texture_float_linear` is often missing on mobile, so filtered float SDF textures are not portable in WebGL1. — [WebGL Fundamentals: cross-platform issues](https://webglfundamentals.org/webgl/lessons/webgl-cross-platform-issues.html)

### Inferences
(Our own derivations / prior knowledge; not measured.)
- **Ray–box clip (we already have the proxy):** compute entry/exit `t0,t1` of the glyph's local box analytically (slab test) in the FS; start at `t0`, stop at `t1`. This removes all steps spent outside the box and is the "bounding volume early exit" in its exact form.
- **Front-cap test, 1 fetch:** if the ray enters through the front face (z = +h), sample the 2D SDF at the entry xy; if `d2 < 0`, the hit is the cap, normal = (0,0,1) (or bevel), done. For a mostly front-facing label this resolves most covered pixels with a single fetch.
- **2D march with scaled steps:** for the extrusion `d = max(d2(xy), |z| - h)`, within [t0,t1] the z-term is handled analytically, so only xy matters; since d2 is 1-Lipschitz in xy, the safe step in t is `d2 / length(rd.xy)`, which is larger than the 3D step `min(d2, …)` whenever the ray is steep (near-frontal view). Clamp with a minimum step to avoid stalling when `rd.xy ≈ 0` (then the ray is effectively a single xy point: hit iff `d2 < 0` at that point).
- **Over-relaxation (from prior knowledge, not re-verified):** step `ω·d` with ω ≈ 1.2–1.6; if the new sphere does not overlap the previous one (`ω·d_prev > d_prev + d_new`), go back and take the plain step with ω = 1. With an 8-bit SDF clamped to its spread, distances are capped anyway, so relaxation helps mainly in the long empty stretches inside the box between strokes. Expect a modest gain; measure with step-count heatmaps.
- **Hit refinement:** keep last two samples (t_a, d_a > 0) and (t_b, d_b < 0) and do one secant step `t = t_a + (t_b - t_a)·d_a/(d_a - d_b)`; one extra fetch removes 8-bit stair-stepping on the side walls better than more march steps. Binary refinement (2–3 bisection steps) is the robust alternative.
- **Allow overshoot to cut the step cap:** with hit threshold based on pixel footprint (`eps = k·t·pixelAngle`, k≈0.5–1), marching stops earlier at distance and coverage AA from the closest-miss already uses the same quantity — consistent with "cone tracing for AA" (closest-miss/footprint gives coverage).
- **Fewer texture fetches:** our SDF (LUMINANCE) and mask/normals (RGBA) are separate textures → 2 fetches per step if both are read in the loop. Pack SDF into the A channel of the RGBA mask texture (normals in RG, extra in B) and read normals only once at the hit. Do not sample the mask inside the loop.
- **8-bit SDF precision:** 256 levels over the spread; e.g. spread ±8 px → 1/16 px resolution, bilinear filtering helps. Outside the spread distances clamp → march slows; make the box proxy tight and the spread ≥ the typical gap between strokes. Two-channel 16-bit packing (hi/lo bytes) breaks hardware bilinear filtering (filtering hi and lo separately is wrong), forcing 4 manual fetches — usually not worth it; a larger atlas or spread is cheaper. MSDF gives sharp corners at low resolution but its median is not a true distance far from the edge; for marching, MTSDF (MSDF + true SDF in alpha) is the variant to consider (msdfgen, prior knowledge).
- **Step cap as a quality knob:** after the analytic tricks above, MAX_STEPS 16–24 is likely sufficient for frontal/moderate angles; keep 40+ only for strong rotations (flip animations). This maps directly to the shader-variant idea in section 1.
- **Debug view:** a heatmap of steps per pixel (brightness = steps/MAX_STEPS) is the standard way to see where budget goes (as in the Cambridge example).

## 6. Battery/thermal measurement and practical budgets

### Takeaway
Browsers expose almost no direct thermal/battery signal; the practical proxies are rAF frame period over time (sustained slowdown = throttling) and on-device profiling tools. iOS caps rAF to 30 fps in Low Power Mode by design, and cross-origin iframes are throttled until user interaction — both must be distinguished from GPU overload. A decorative effect should be bursty (only while animating, which we already do) and keep its per-frame GPU time small.

### Cited Findings
- iOS throttles requestAnimationFrame to 30 fps in Low Power Mode; a WebKit engineer said this is intentional (the iOS 13 behaviour was the bug); implemented by running the display refresh monitor at 30 fps. — [WebKit Bug 215745](https://bugs.webkit.org/show_bug.cgi?id=215745)
- iOS Low Power Mode also throttles CSS animations (developer report); cross-origin iframes are throttled until the user interacts with them. — [popmotion: When iOS throttles rAF](https://popmotion.io/blog/20180104-when-ios-throttles-requestanimationframe); [motion.dev: when browsers throttle rAF](https://motion.dev/magazine/when-browsers-throttle-requestanimationframe)
- 2024 WebKit report: the low-power cap also applies to animations with `linear()` easing, "as designed". — [WebKit Bug 281429](https://bugs.webkit.org/show_bug.cgi?id=281429)
- No known way to force 60 fps in Low Power Mode; advice is to respect the throttling. — [GreenSock forum](https://greensock.com/forums/topic/26826-any-way-to-keep-gsap-running-at-60fps-while-mobile-device-is-in-low-power-mode/)
- `getError`/`getParameter` stall up to ~1 ms, so they must not be used for in-loop measurement. — [MDN WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)
- On-device shader cost tools: Arm Mali Offline Compiler (cycle estimates for Bifrost, e.g. Mali-G52). — [Arm blog](https://developer.arm.com/community/arm-community-blogs/b/mobile-graphics-and-gaming-blog/posts/accelerating-shader-programs-with-mali-offline-compiler-7)
- A low-end GPU can be ~100x slower than a top-end one. — [WebGL Fundamentals: cross-platform issues](https://webglfundamentals.org/webgl/lessons/webgl-cross-platform-issues.html)

### Inferences
- Measurement recipe for the prototype (fits our Debug → «Замер»): log rAF deltas per animation, plus a synthetic "steps x pixels" estimate (pixels drawn x average steps from a heatmap readback in debug only); watch for sustained FPS decay over 2–5 minutes of repeated animations (thermal throttling signature) rather than single-frame spikes. Distinguish a stable 33.3 ms period (Low Power Mode cap) from irregular long frames (GPU overload).
- Telegram Web/Desktop embed Mini Apps in an iframe (cross-origin) → rAF may be throttled until the user taps; do not treat that as low performance.
- Budget (inference, no source): at 60 fps the whole frame is 16.7 ms and the WebView compositor, DOM animations and our WebGL backdrop share it; a decorative text effect should target ≤ 2–3 ms GPU per frame on iPhone 11 and accept lower resolution/steps on Mali-G52 to stay ≤ 4 ms. Bursty use (≤ 1–2 s per animation, idle = no rendering, canvas hidden) is what keeps the device cool, in line with our existing rule that iPhones heat from constant work, not one-off effects.
- Xcode Instruments (Safari/WKWebView remote) and Android GPU Inspector / Snapdragon Profiler are the real tools for GPU time and thermal state on device (prior knowledge).
